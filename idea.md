# Nook — личное хранилище документов с быстрым поиском

> **Nook** — второе хранилище для «важного, но не хочу потом долго искать».
> Не бэкап, не поиск по всему диску, не второй диск.

---

## 1. Проблема

Студент на удалёнке / разработчик накапливает документы, которые «важные, но
не хочется потом долго искать». Они расползаются по `Downloads`, `Desktop`,
почте, мессенджерам. Стандартный поиск Windows — медленный и неудобный.

## 2. Позиция продукта

Nook — **второе хранилище** для важного, но не для всего подряд.
Пользователь сознательно решает, что достойно зоны; Nook гарантирует, что
через полгода это найдётся за секунды.

**Следствия:**
- Добавление: drag & drop файлов, одного или нескольких — MVP.
  Импорт из папки через диалог с чекбоксами (пользователь видит, что
  добавляет) — should, позже. Рекурсивный drag & drop папки — won't.
- «Вместе» организуется **тегами**, не физическими папками.
- Фильтр срабатывает в голове пользователя **до** попадания в зону.
- README: «Nook не заменяет бэкап». Кнопка «экспорт в zip» — удобство
  переноса, а не защита от потери диска.

**Чем Nook не является:**
- Не поисковик по всему диску (это Everything / FilePulse / Kensaku).
- Не бэкап.
- Не облако / синк.
- Не Todoist (никаких приоритетов, дедлайнов и естественного языка).

**Потенциальные пользователи (за пределами MVP):**
Логисты, бухгалтеры, юристы, HR — все, у кого поток документов со слабой
структурой имён. НО: их сценарии отличаются (синк, поиск по содержимому
PDF, версии, «не удалять никогда»). Это отдельные фичи, не в MVP.
MVP — для себя, доказать, что работает. Если взлетит — расширять по одному
сценарию за раз.

## 3. Целевой сценарий

1. Скачал важный документ → drag & drop в окно Nook → файл в зоне, запись в базе.
2. Через полгода помню «что-то про практику» → ввожу `практ` в поиск →
   за миллисекунды вижу список с датами и размерами → открываю нужный.
3. Кинул файл дважды → Nook говорит «уже есть, вот он» → второй раз не добавляет.
4. Кинул 3 файла по курсовой → повесил тег `#курсовая2024` → через год
   ищу `#курсовая2024`, вижу все три вместе.

## 4. Критерии

### Must
- **Хранение**: физическая зона, файлы реально переезжают в выбранную папку.
- **Добавление**: drag & drop одного или нескольких файлов.
- **Поиск**: fuzzy по нормализованному имени (`rapidfuzz`), мгновенный.
- **GUI**: строка поиска + таблица результатов + drag & drop.
- **Дедупликация**: SHA-256 содержимого при добавлении.
- **Корзина**: удаление в `trash/`, а не `os.remove`.
- **Теги**: добавление при импорте и на существующие файлы, автодополнение,
  поиск `#тег`. Теги — основной способ «собрать вместе».

### Should
- Инлайн-фильтры в строке поиска (`\ #тег [дата]`).
- Панель фильтров в GUI (дата-пикер, чекбоксы типов) рядом со строкой поиска.
- Заметки к файлам (`note`).
- Массовое удаление по критериям (дата, расширение).
- **Массовое проставление тега**: выделить N файлов → повесить тег.
- **Переименование и слияние тегов** (лечит опечатки).
- **«Импорт из папки»**: обход папки → список с чекбоксами → пользователь
  отмечает важное → добавляется только отмеченное, опционально с общим
  тегом = имя папки. Тот же осознанный фильтр, просто автоматизированный.
- **Quick add / Inline syntax**: command palette (Ctrl+K), live-поиск.
- Лог запросов с 0 результатов — карта дыр в зоне.
- Превью файлов в результатах.

### Won't
- **Шифрование** — нет модели угроз, боль при переустановке, неделя времени.
- **Виртуальный индекс чужих папок** — превращает в поисковик, ломает бэкап,
  тянет `watchdog` на чужие папки и реконсиляцию.
- **Рекурсивный drag & drop папки** — молчаливое добавление всего содержимого,
  свалка внутри зоны, обход фильтра пользователя.
- **Папка как физическая сущность / архив (zip)** — ломает плоское хранение,
  содержимое архива не ищется.
- **Иерархия тегов через parent_id** — слэш-конвенция (`#учёба/курсовая`)
  достаточна и обратно совместима.
- **Дедуп по имени** — молча теряет данные (v1/v2 договора).
- **Автосуффикс `(2)` в имени** — косметика, врёт о содержимом.
- **Синк / облако**.
- **Поиск по хешу** — хеш не годится для fuzzy, только для точной проверки.
- **PyPI / pip-установка** — распространение через `.exe` + инсталлятор.
- **Естественный язык в поиске** (завтра, важное) — это Todoist-семантика.

## 5. Решение по зоне

**Физическая зона** [решено]. Файлы реально живут в выбранной пользователем
папке (по умолчанию `%APPDATA%\nook\vault\` или `~/Документы/Nook/`).

- Плоская структура на диске: `vault/files/<uuid>.<ext>`.
- Человекочитаемое имя — в базе (`original_name`).
- «Вместе» — через теги, не через папки на диске.
- Корзина: `vault/trash/` вместо удаления.
- Данные приложения (SQLite, конфиг, лог): `%APPDATA%\nook\` через `platformdirs`.

**Главный риск:** пользователь не кидает файлы в зону → зона пустеет.
Митигация: drag & drop на старте (must), хоткей / Send-to (should),
импорт из папки (should).

## 6. Модель данных (SQLite)
```sql
files(
    id            INTEGER PRIMARY KEY,
    original_name TEXT NOT NULL,      -- имя как было у пользователя
    stored_path   TEXT NOT NULL,      -- vault/files/<uuid>.<ext>
    hash          TEXT NOT NULL,      -- SHA-256 содержимого
    size          INTEGER NOT NULL,
    added_at      TIMESTAMP NOT NULL, -- дата добавления в зону
    mtime         TIMESTAMP,          -- дата изменения файла
    note          TEXT,               -- заметка (should)
    source        TEXT                -- откуда добавлен (should)
)

tags(
    id   INTEGER PRIMARY KEY,
    name TEXT NOT NULL                -- как ввёл пользователь
)
-- уникальность и поиск по lower-case:
CREATE UNIQUE INDEX idx_tag_lower ON tags(LOWER(name));

file_tags(
    file_id INTEGER NOT NULL REFERENCES files(id) ON DELETE CASCADE,
    tag_id  INTEGER NOT NULL REFERENCES tags(id)  ON DELETE CASCADE,
    PRIMARY KEY(file_id, tag_id)
);

search_log(id, query, results_count, ts)  -- should, для карты дыр

CREATE UNIQUE INDEX idx_hash ON files(hash);
CREATE INDEX idx_added_at ON files(added_at);
```

**Почему не key-value:** SQLite — реляционная БД. Модель — картотека,
не KV-стор. FTS5 доступен при необходимости поиска по содержимому (позже).

## 7. Теги

Теги — **основной способ «собрать вместе»** без физических папок.
Файлы лежат плоско, «вместе» = общий тег.

**Плоские, не иерархия (MVP).** `#курсовая2024`, `#диплом`.
Слэш-конвенция (`#учёба/курсовая`) — позже, обратно совместимо.

**Потоки (must):**
- При добавлении файла: поле «теги» с автодополнением.
- На существующем: колонка «теги» в таблице, «+» → автодополнение.
- **Массово (should):** выделил N файлов → «повесить тег на выделенные».

**Нормализация:** поиск и уникальность — по lower-case (`LOWER(name)`),
хранение — как ввёл пользователь. `ё→е`.

**Чистка:** при старте: `DELETE FROM tags WHERE id NOT IN (SELECT tag_id FROM file_tags);`

## 8. Синтаксис поиска: Разделение имени и параметров

Чтобы избежать коллизий с именами файлов (где есть скобки и решетки) 
и проблем с раскладкой, вводим разделитель.

- **Формат:** `<Текст для поиска> \ <Параметры>`
- **Разделитель:** `\` (клавиша над Enter, **без Shift**). В будущем можно 
  добавить поддержку `/` (для английской раскладки), не ломая логику.
- **Левая часть:** всегда чистый текст для fuzzy-поиска по имени.
- **Правая часть (Параметры):** 
  - Теги: `#тег` (или `№тег` на русской раскладке)
  - Даты: `[12.04.2020]`, `[<12.04.2020]`, `[12.04.2020,31.12.2024]`
  - Отрицание: `-#тег`, `-[<12.04.2020]`

**Примеры:**
- `практ \ #курсовая [<12.04.2020]` — ищем "практ", фильтруем по тегу и дате.
- `Отчет №5 (копия)` — ищем файл с таким именем (разделителя нет, всё текст).
- `договор` — просто ищем по имени.

**Пайплайн запроса:**
1. Сплит по `\`. Левая часть -> fuzzy, правая -> парсер.
2. Левая часть нормализуется (lower-case, `ё→е`, разделители → пробел).
3. Правая часть парсится регулярками на теги и даты.
4. Жёсткие фильтры отсекают кандидатов (дата, тег).
5. `rapidfuzz.process.extract` по оставшимся, `scorer=WRatio`, `score_cutoff=60`.

### Расширение файла в названии
Если в левой части (до разделителя `\`) есть точка, и после неё идет 
строка длиной от 2 до 15 символов, состоящая ТОЛЬКО из латинских букв 
(a-z, A-Z), это распознается как фильтр по расширению.
- Из названия расширение убирается (для fuzzy-поиска).
- В запрос к БД добавляется `WHERE original_name LIKE '%.ext'`.
- Если после точки есть цифры, кириллица или больше 15 символов 
  (например, `отчет.2024`, `лекция.Часть1`), это считается частью имени файла.

Примеры:
- `смета.xlsx` -> текст "смета" + фильтр расширения "xlsx"
- `архив.torrent` -> текст "архив" + фильтр расширения "torrent"
- `отчет.2024` -> текст "отчет.2024" (расширения нет)

Примечание: Даты в квадратных скобках [12.04.2020] по умолчанию фильтруют по дате добавления в зону (added_at). Фильтры по дате изменения (mtime) можно добавить отдельным синтаксисом позже.

## 9. Дедупликация

**SHA-256 содержимого при добавлении** [must]. Не поиск, а проверка
существования при вставке: `SELECT WHERE hash = ?`, O(1) по уникальному индексу.

- Нашлось → «Уже есть: `<имя>`, добавлен `<дата>`», второй раз не добавляем.
- Не нашлось → копируем/перемещаем в зону, пишем в базу.

**Разные файлы с одинаковым именем** — легитимны (v1/v2, ежедневные отчёты).
Дедуп по имени **не делаем** (молча теряет данные). Различаем в выдаче
через `added_at` + `size`.

## 10. Удаление

- Единичное → в `trash/`, восстановление возможно.
- По критериям (дата, расширение) → тот же парсер параметров, что и поиск.
- Массовое выделение в таблице → ручная сортировка → удаление.

## 11. Архитектура (MVC)

Используется паттерн **MVC (Model-View-Controller)**, который естественно
складывается при использовании PyWebview.

```text
nook/
├── __init__.py
├── model/            # Модель (чистая логика)
│   ├── zone.py       # CRUD файлов в зоне (и os.startfile для открытия)
│   ├── db.py         # SQLite: схема, миграции
│   ├── index.py      # индекс в памяти (dict)
│   ├── search.py     # rapidfuzz + применение фильтров
│   ├── query.py      # parse_query, parse_bracket, parse_date
│   ├── tags.py       # CRUD тегов, слияние, чистка
│   ├── dedup.py      # SHA-256
│   └── config.py     # platformdirs, настройки
├── view/             # Представление (чистый UI)
│   ├── index.html
│   ├── style.css
│   └── app.js
└── controller/       # Контроллер (тонкий диспетчер)
    └── main.py       # Класс Api (связь JS -> Python), запуск окна
```

**Правила:**
- **Model** ничего не знает про UI и PyWebview. Чистые функции и классы.
- **View** ничего не знает про SQLite и Python. Только HTML/CSS/JS и вызовы `pywebview.api`.
- **Controller** (`main.py`) — тонкая пленка. Принимает JSON от JS, вызывает методы Model, отдает JSON обратно.

**Потоки:** индексация и поиск не блокируют UI. Первичная индексация —
прогресс-бар. Обновление индекса в фоне — `watchdog` на одну папку зоны.

## 12. GUI (PyWebview)

**Фреймворк:** PyWebview (Python + HTML/CSS/JS) [решено].
- Python — бэкенд (поиск, БД, файлы).
- HTML/CSS/JS — фронтенд (интерфейс, анимации, стили).
- Связь через `js_api` (JS вызывает Python-методы, получает JSON).
- Зависимости
  + `pywebview` — GUI-окно и мост JS <-> Python
  + `rapidfuzz` — нечёткий поиск (fuzzy)
  + `platformdirs` — правильные пути к AppData на разных ОС
  + `watchdog` — слежение за изменениями в папке зоны (should)
  + `pytest` — для тестов (dev-зависимость)

**Ввод на русской раскладке (UX) [решено]:**
Пользователь печатает в той раскладке, которая включена (обычно русская).
Спецсимволы `#` и `[ ]` требуют переключения языка.
- Парсер (Python) понимает `#` и `[ ]` (чистый синтаксис).
- View (JS) на лету перехватывает нажатия в зоне параметров (после `\`):
  - `№` (Shift+3) -> `#`
  - `(` (Shift+9) -> `[`
  - `)` (Shift+0) -> `]`
- Это позволяет не заставлять пользователя переключать раскладку.

**Экраны (MVP):**
- Главное окно: строка поиска, таблица результатов (имя, дата, размер, теги),
  drag & drop зона, кнопка «добавить файл», поле тегов при добавлении.
- **Quick add / Inline syntax**: command palette (Ctrl+K), live-поиск.

**Стиль:** тёмная тема, неоновые акценты, градиенты.

## 13. Сборка и распространение

**PyPI не нужен** — GUI + `.exe`, пользователь не ставит Python.

- **Инструмент:** PyInstaller (`--onedir --windowed`).
- **Важно:** упаковать папку `view/` внутрь `.exe` (флаг `--add-data "view;view"`).
- **Собирать рано** (на середине проекта) — проверить на чистой машине без Python.
- **Инсталлятор:** Inno Setup или NSIS поверх `--onedir`.
- **Данные:** `%APPDATA%\nook\` (не рядом с `.exe`).
- **CLI-точка входа** — только для тестов и разработки.

## 15. Журнал решений

| Решение | Причина |
|---|---|
| Имя: Nook | Закрыто |
| Физическая зона | Хранилище, а не поисковик; консистентный индекс |
| Плоское хранение `<uuid>.<ext>` | Нет коллизий на диске, имя в БД |
| `rapidfuzz`, не хеш | Хеш не ищет «примерно», только точно |
| SHA-256 для дедупа | Проверка существования при вставке |
| Дедуп по имени — нет | Молча теряет данные (v1/v2) |
| Папка как сущность — нет | Ломает плоскость, свалка; «вместе» через теги |
| Теги — основа организации | Не тянут рекурсию, дают «вместе» |
| Теги плоские, не иерархия | Слэш-конвенция позже, обратно совместимо |
| Уникальность тегов по lower-case | Иначе `#Курсовая` и `#курсовая` — разные |
| Разделитель `\` в запросе | Без Shift, нет коллизий с именами файлов |
| Автозамена в JS (`№` -> `#`, `(` -> `[`) | Русская раскладка, скорость ввода |
| GUI на PyWebview | Опыт с JS/CSS, кастомный дизайн |
| Архитектура MVC | Естественно ложится на PyWebview, тестируемость |

## 16. Порядок работ

1. **Model** без UI: `zone.py`, `db.py`, `index.py`, `query.py`, `search.py`,
   `tags.py`, `dedup.py`. Тесты через `pytest` + минимальный CLI.
2. **Controller** (`main.py`): класс `Api` с методами поиска и добавления.
3. **View**: базовая верстка HTML/CSS, таблица, строка поиска.
4. **Интеграция**: связать View и Controller через `pywebview`.
5. **Фоновая индексация** через `watchdog` + поток.
6. **Сборка `.exe`** — на середине, проверить на чистой машине.
7. **Инсталлятор** — в конце.
8. **Полировка**: README с гифкой, бенчмарки, раздел «Query syntax».
